# T3 dispatch contract design

**Intent:** Turn the frozen T3 taxonomy into an explicit, testable production operation boundary without coupling it to the legacy seven-label prototype or claiming that unconnected services have answered a query.

## Boundaries

`src/nlp_v2/` owns the production T3 contract. Historical Gate B.2/B.3 scripts, labels, manifests, and checkpoints remain untouched. This phase accepts a structured prediction and canonical slot values supplied by callers; extraction, model inference, and canonical KB services follow in later phases. The operation names come from `data/nlp_v2/taxonomy/taxonomy_semantic_mapping.json`.

## Input and output

`IntentPrediction` carries a primary T3 label or `None`, an acceptable-label set, a confidence in `[0, 1]`, and an optional clarification reason. A `None` primary or explicit `multiple_goals` reason requests clarification rather than arbitrarily choosing one operation. `dispatch(prediction, slots, service)` yields a serializable result with intent, operation, status, slots, missing slots, message, and data. Status values are `ok`, `clarification`, `unavailable`, `out_of_scope`, and `error`.

The dispatcher validates the label and confidence, canonical slot names and types, bounded enum values, and required or conditional slots before calling the service. It rejects forbidden intent-slot combinations for executable single-intent predictions. An unknown/malformed prediction raises a contract error. Missing execution slots yield `clarification` and do not call the service. Genuine intent ambiguity, entity uncertainty, temporal ambiguity, and multiple goals also yield `clarification`, with a distinct reason. A bare `kal` without a resolved date and a time candidate set with more than one value cannot execute. The realtime class always returns `unavailable`; out-of-scope always returns `out_of_scope`, before temporal clarification. The two route intents accept canonical `locality` references.

## Required information

Route planning and mode availability require origin and destination. Stop sequence requires a route number. Stop membership requires route number and stop. Scheduled departure requires a station or stop. Fare calculation requires an origin/destination pair or a stage number. Facilities and accessibility require a station. Interchange requires a station or both transfer modes. Nearest transport requires a landmark or locality. First/last service, frequency, and ticketing are allowed without a mandatory slot because users can ask general policy or system-wide questions; service implementations may report `unavailable` when the specific data requested is not present. Optional slots are preserved for services; an unknown canonical slot is rejected, never guessed.

## Service boundary

A domain service exposes `execute(operation, slots) -> ServiceResult`, returning an explicit state, structured data, and a human-readable message. The default service returns `unavailable` for all unconnected operations. No transport fact is generated by the dispatcher. Later phases replace this service with canonical DB queries while retaining the same contract.

## Verification

Table-driven tests cover all 16 literal T3 labels and operation names, missing and conditional slots, ambiguity and multiple goals, typed and forbidden slot combinations, invalid input, and service status propagation. They assert behavior using a small recording service and never use held-out queries.
