## Confirmed mechanisms

**Raw frozen-classifier decisions are terminal single labels.** `src/nlp_v2/model.py:101` tokenizes the original query, truncates to 64 tokens, takes argmax and returns a singleton acceptable-label set. It does not return calibrated ambiguity or alternative candidates. `src/nlp_v2/assistant.py:189` consumes that family, and downstream source refusals faithfully execute the chosen family. This directly explains why a wrong-family safe response remains wrong: the source layer cannot recover missing semantics. The exact learned reason for any label cannot be established from source inspection alone; negation, colloquial/transliterated wording and OOS examples are observed failure clusters, not proved training causes. Broad reliable understanding would require separately governed, independent development/model work; it cannot honestly be claimed from numeric or UI fixes.

**Independent source gates intentionally skip extraction.** `assistant.py:208-214` checks family capability before extraction. `domain.py:114-143` reports absent authoritative ticket policies, unverified facilities, missing confirmed multimodal/interchange graphs or null accessibility values. Thus many correct-family replies have `{}` slots by design. They are safe source limitations, with feature/mode extraction unverified; absence of slots alone is not proof of misrecognition in these paths. The mode source gate at `assistant.py:241-247` runs after extraction but before missing/ambiguous input dispatch, explaining source refusals that expose secondary wrong/missing endpoints or clocks.

**Route extraction requires an adjacent explicit bus/route cue.** Baseline `slots.py:194-242` normalizes Unicode digits correctly but only accepts route codes next to `bus`, `bs`, `route`, `बस` or `रूट`. A bare code followed by `ka`, `ki`, `ke`, `me`, or a stop name has no recognition path. This explains why HG200_032's `१०२A bus` works while HG200_033's `२५R ki...` does not; it also explains HG200_061's `25R Poonamallee...` and HG200_075's `102 ke...`. In HG200_050, lost 25R plus wrong last/departure family allows a general departure query to execute on unrelated routes. Preserving a structured user route constraint or clarifying an explicitly detected but unsupported route is safer than silently deleting it. A general route parser must distinguish route codes from clocks, stage counts and unrelated numbers rather than accept every bare number.

**Stage grammar is one-directional.** Baseline `slots.py` fare extraction accepts only `(stage|स्टेज) + digits`, as does its competing-stage guard (`slots.py:312-317`). The reverse forms `11 stages` and `8 stage` are not matched, and the native numeral in HG200_102 is also before its noun. Python's `\d` already recognizes Devanagari decimal digits: these Hinglish-stage failures primarily expose reversed/plural grammar, not proof of a digit-conversion bug. General stage parsing should recognize explicit noun/count order in both directions while preserving class and stage range, and count all coordinated explicit stage mentions.

**Daypart applies only in the baje/o'clock branch.** Baseline `_time` at `slots.py:245-284` checks AM/PM, then a branch requiring `baje`/`बजे`/`o'clock`, where shaam/raat/subah are applied. A colon time without that suffix falls through to the 24-hour branch. Therefore `shaam 6:20 ke baad` produces 06:20, matching HG200_076. Associate an explicit daypart with the clock regardless of the word baje, retaining invalid/ambiguous cases rather than silently defaulting.

**Mode vocabulary and extraction ignore negation scope.** Baseline `MODE_PATTERNS` recognizes `bus`, not plural `buses`, and `local train`, not bare colloquial `local`; line names do not automatically provide a mode. It scans all mode mentions, including `bus bilkul nahi` and `bus...mat ginna`, then `assistant.py:217-223` asks for one mode. This mechanism explains HG200_012/096 and avoidable bus/rail ambiguity in HG200_051/065. A general semantic request representation should retain requested/excluded modes and distinguish reference-location modes from target modes. An explicit UI mode default can provide absent mode context, but cannot fix a wrong classifier family or override explicit requested/excluded modes.

**Goal and scope guards use lexical hits, not clause semantics.** `assistant.py` splits coordination and chooses the first matching cue per clause; cues include route, fare, ticket, live, parking and lift, with no negation analysis. `slots.py:290-333` counts line/route/time/day and candidate-identity sets. `_unknown_timetable_coordination` attempts to protect unknown extra stops using bounded modifier syntax. These guards prevent some genuine competing scopes (HG200_194/195/196/198/200) but cannot distinguish every courtesy/explanation/negation clause from a second goal/location. HG200_053/056/057/069/083/084 and nearest examples receive false scope prompts. Exact aliases can also match incidental words inside missing-input prose (HG200_164). The individual false-positive source cannot be fully distinguished without diagnostic span metadata; classify this mechanism as a source-grounded hypothesis, not a proven case-specific alias. Avoid adding query-specific guard exceptions. Parse explicit positive goals/roles into a representation and base cardinality on that representation; retain unsupported extra scopes for transparent clarification.

**Exact span resolution can conflate locality and stop.** `entities.py:126` greedily finds longest exact aliases without syntactic-role filtering. In proximity queries, `entities.py:150-153` prefers place candidates but falls back to physical stops/hubs. `slots.py` assigns the first nearest span as landmark. This explains why an unqualified Thiruvanmiyur can become a physical bus-stop anchor and return itself at 0 m. An explicit user reference type or a transparent anchor confirmation can distinguish a locality center from a station/stop reference; a new factual place coordinate must come from verified source data, not a QA expectation.
